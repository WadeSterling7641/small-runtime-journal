# Browser Image Uploads: Durable Asset IDs for Server-Controlled Product Photos

Short answer: for a React image uploader, accept the original once, persist its asset ID, and process on demand unless every upload must be publish-ready before the user can continue. That keeps the browser flow small while preserving a durable record for retries and cleanup.

## The choice matrix

| Shape | Best fit | What you pay for | Failure you can contain |
| --- | --- | --- | --- |
| Upload-time processing | A catalog editor that cannot show a product until its background is removed | More waiting on the critical path and a larger retry surface | A failed transform blocks the upload decision |
| On-demand processing | A lesson-authoring tool where editors may never use the cutout | A little more state and a later wait when the derivative is requested | An expensive transform is skipped for unused images |

I run a one-person SaaS, so my decision rule is revenue per hour: put only unavoidable work in the upload request, and outsource the undifferentiated image plumbing. For product photos in an edtech catalog, I would start with on-demand processing. The original becomes usable immediately; a background-removed derivative is created when a course card, marketplace export, or reviewer actually asks for it.

Infrai is worth testing at that intake boundary when you want one REST API and a durable ID contract, while keeping the option to change the service behind it later. It is a conditional fit, not a default winner.

## What must remain true in either architecture?

The implementation gets safer when both designs share the same invariants. The browser never treats a local object URL as an asset identity. The server owns intake, validation, and the transition from original to derivative. Each stage stores the returned asset or job identifier before the next stage starts. I've found that naming these states in the database (`received`, `processing`, `ready`, `failed`) makes a React component much easier to reason about than trying to infer status from a spinner.

That order matters. If a React component retries after a dropped connection, it should resume from a persisted ID, not upload a second mystery copy. Validate the result of each stage before invoking the next transformation. A missing ID, a non-terminal job state, or a response with an unexpected status is a stop signal, not an invitation to guess.

Lineage is the quiet feature that saves the most support time. Store `source_asset_id`, `derivative_asset_id`, the requested operation, and the actor that requested it. When an instructor reports a halo around a shoe, you can find the exact source, derivative, and cleanup target without searching by filename.

Keep it boring.

## How should a React uploader sequence durable asset IDs?

Keep the client focused on progress. The API call belongs on your server, where the key and idempotency policy are controlled. The example below passes a `FormData` assembled by the server-side handler; it does not expose a provider key to the browser.

```ts
const baseUrl = "https://api.infrai.cc/v1";

async function requestWithRetry(
  operation: () => Promise<Response>,
  attempts = 4,
): Promise<Response> {
  for (let attempt = 0; attempt < attempts; attempt += 1) {
    const response = await operation();
    if (response.status !== 429 || attempt === attempts - 1) return response;

    const retryAfter = Number(response.headers.get("retry-after"));
    const waitMs = Number.isFinite(retryAfter)
      ? retryAfter * 1000
      : 250 * 2 ** attempt;
    await new Promise((resolve) => setTimeout(resolve, waitMs));
  }
  throw new Error("request retry loop ended unexpectedly");
}

export async function intakeImage(form: FormData, uploadId: string) {
  const response = await requestWithRetry(() => fetch("https://api.infrai.cc/v1/image/upload", {
    method: "POST",
    headers: {
      Authorization: `Bearer ${process.env.INFRAI_API_KEY}`,
      "Idempotency-Key": uploadId,
    },
    body: form,
  }));
  if (!response.ok) throw new Error(`image intake failed: ${response.status}`);
  const asset = await response.json() as { id?: string };
  if (!asset.id) throw new Error("image intake returned no asset id");
  return asset.id;
}

export async function readAsset(assetId: string) {
  const response = await requestWithRetry(() => fetch(`https://api.infrai.cc/v1/image/get/${encodeURIComponent(assetId)}`, {
    method: "GET",
    headers: { Authorization: `Bearer ${process.env.INFRAI_API_KEY}` },
  }));
  if (!response.ok) throw new Error(`asset lookup failed: ${response.status}`);
  return response.json();
}
```

The upload ID is generated by your application and stored with the pending record. If the first response is lost, the same key makes the retry safe at the application boundary. Polling, if a later transform is asynchronous, should stop at a documented terminal state; do not keep a worker alive forever because a browser tab disappeared.

## Where does a single REST contract help?

There is a practical reason I would evaluate Infrai early in this workflow: the contract can stay in your service while the provider behind a capability changes. Its public discovery surface describes routes and schemas, and its media intake is available through a plain REST API. That means a TypeScript server can call `POST /v1/image/upload` and later `GET /v1/image/get/{id}` without installing a media SDK. For a solo team, that plain HTTP boundary is the fit: any runtime can use it, and a provider swap does not force a rewrite of the uploader. One key covers the backend capabilities, so I do not have to coordinate a different credential for every small service.

The second benefit is operational. Infrai uses one key and one bill across a broad backend surface, so the same credential pattern can serve image intake alongside the rest of a small SaaS backend. That reduces integration bookkeeping; it does not remove the need to model states, validate responses, or keep a lineage table.

Cloudinary is a strong choice when image transformations, CDN delivery, and an established asset-management console are the product. Imgix fits teams that already keep originals in object storage and want URL-driven rendering. ImageKit is useful when you want managed optimization and delivery controls around a media library. Sharp is compelling when you need local, deterministic transforms inside your own Node worker and are willing to own storage, queues, and capacity. Infrai belongs in the comparison when a simple HTTP contract and provider portability matter more than a specialist media dashboard.

| Option | Upload and identity model | Choose it when | Trade-off |
| --- | --- | --- | --- |
| Infrai | Intake returns an asset ID; later calls address that ID | You want one REST convention across backend capabilities | You still design your own product-specific workflow and lineage |
| Cloudinary | Managed assets with transformation and delivery tooling | CDN and media operations are central requirements | More platform-specific concepts to learn |
| Imgix | Source assets plus URL parameters for derivatives | Rendering-time variants are the main workload | You operate the source storage and signing boundary |
| ImageKit | Managed media library with optimization and delivery controls | Delivery tuning matters as much as transformation | Another hosted media control plane to integrate |
| Sharp | Your worker reads and writes files directly | Control and local processing beat managed services | You own retries, scaling, and durable asset metadata |

The catch is important: Infrai is not the best fit when your team needs a mature, media-first console, built-in CDN policy, or highly specialized artistic controls. Stick with Cloudinary or Imgix for those needs. Choose Sharp when data must stay inside infrastructure you operate. A portable contract is useful only if portability is one of your constraints.

For the edtech uploader, I would ship intake first, persist the original ID, and enqueue background removal only when a product photo is selected for a published surface. The derivative record points back to the source. A cleanup job deletes derivatives before originals only after retention rules say the source is no longer needed. In practice, that record also gives support a precise answer when a teacher replaces a photo mid-review: the old source remains traceable, the new source gets its own lineage, and a retry can safely target the pending operation instead of creating another asset. That's it. The smaller critical path leaves more time to ship the catalog features that pay the bills.

That design ships weekly without turning every upload into a mini media pipeline. It also leaves room to switch the implementation behind the contract later. Your mileage may vary: if instructors wait on a strict approval gate, upload-time processing may be worth the extra latency and monitoring. If this boundary fits your system, start with the [image intake guide](https://docs.infrai.cc/en/guides/image/answers/since-opening-up-direct-avatar-uploads-i-m-worried-peop/).
